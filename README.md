# Property AI

A NestJS + PostgreSQL API and a Nuxt frontend that replicate the `property-ai-api` Laravel take-home:
a small property portfolio ("properties") with AI-assisted maintenance work orders, plus JWT
authentication (which the original Laravel app didn't have).

```
property-ai-api/          original Laravel reference app (untouched)
property-ai-api-nest/     NestJS API (TypeORM + PostgreSQL)
property-ai-web/          Nuxt 4 frontend (Nuxt UI + Pinia)
docker-compose.yml         Postgres + Redis + the API + an nginx reverse proxy in front of it
```

## Prerequisites

- Node 20+, pnpm 10+ (`corepack enable` if you don't have pnpm)
- Docker (for Postgres + Redis)

## 1. Install dependencies

```bash
pnpm install
```

## 2. Start Postgres + Redis

```bash
docker compose up -d postgres redis
```

Redis is published on host port **6380** (not the default 6379) to avoid clashing with an
unrelated project on this machine - see the comment in `docker-compose.yml`.

## 3. Configure and run the API

```bash
cd property-ai-api-nest
cp .env.example .env
pnpm run migration:run
pnpm run seed      # 14 properties, 6 work orders, and a demo user
pnpm run start:dev # http://localhost:3000/api
```

Set `GEMINI_API_KEY` in `.env` to use the AI-backed endpoints (`POST /api/work-orders` and
`GET /api/properties/{id}/summary`) - get a free key at https://aistudio.google.com. Without a
key those two endpoints return a clean 502 instead of crashing.

Demo login (seeded): `demo@example.com` / `password123`

## 4. Run the frontend

```bash
cd property-ai-web
cp .env.example .env
pnpm run dev # http://localhost:3000 by default port conflicts with the API - see below
```

The Nest API and Nuxt dev server both default to port 3000. Either run the API on a different
port (`PORT=3001` in `property-ai-api-nest/.env`, and update `NUXT_PUBLIC_API_BASE` in
`property-ai-web/.env` to match) or run Nuxt with `pnpm run dev -- --port 3002`.

## Alternative: full Docker stack

`docker compose up -d` also builds and runs the NestJS API in a container behind an nginx
reverse proxy on `http://localhost:8080/api`. Point `NUXT_PUBLIC_API_BASE` at that URL to run
the frontend against it. Migrations/seed still need to be run once (see step 3, or
`docker compose exec api pnpm run migration:run` / `... run seed`).

## What's here

- **Properties** (`GET /api/properties`, `/{id}`, `/stats`, `/{id}/summary`) - filter/sort parity
  with the Laravel original, plus the optional AI building-summary and stats endpoints.
- **Work orders** (`GET /api/work-orders`, `POST /api/work-orders`) - the AI pipeline (Gemini)
  turns a free-text maintenance request into a structured work order; invalid AI output is
  retried once and never partially saved.
- **Auth** (new - the Laravel app had none): JWT access + refresh tokens, refresh tokens tracked
  in Redis so they can be revoked/rotated on refresh and logout. All `properties`/`work-orders`
  routes require a bearer token.
- Rate limiting (10 req/min, Redis-backed) on the two AI-backed endpoints, mirroring the
  original's `throttle:10,1` middleware.
- Tests: `pnpm test` (unit) and `pnpm run test:e2e` (e2e, against a disposable Postgres schema)
  inside `property-ai-api-nest`.

## Known simplifications vs. the original / a production build

- Email validation is RFC-format only (no DNS/MX lookup like Laravel's `email:rfc,dns`).
- The frontend stores JWTs in a plain (non-httpOnly) cookie, standard for a decoupled SPA + API
  but not the most XSS-resistant option; a same-origin BFF proxy would be the harder-but-safer
  alternative.
- Prefixed IDs (`P-001`, `WO-1001`) are generated by querying the highest existing ID, same as
  the original - not race-safe under heavy concurrent writes.
